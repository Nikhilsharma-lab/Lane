# Storybook visual review

This harness runs isolated production-component stories. It does not import the app E2E configuration, load `.env` files, provision Clerk users, or connect to a database. Storybook owns the fixture data.

The matrix is Chromium at 1440 × 1000 and 390 × 844, each in light and dark mode. It fixes the date to 2026-09-30T08:00:00Z, locale to en-US, timezone to UTC, scale to 1, and reduced motion to `reduce`. Fonts and each story's interaction function finish before capture; the shared preview hook exposes the completion marker. The TextField image therefore captures its entered example text, not an arbitrary frame during typing. Interactive behavior is also covered by the Storybook Vitest suite.

The foundation specimen renders the installed Arc components with Lane's production Arc foundation tokens. Product flow stories use the real Lane components with isolated fixture data and mocked actions. Candidate capture does not turn fixture states into evidence of a successful hosted Clerk, database, or attachment journey.

## Capture candidates

```sh
pnpm exec playwright test --config playwright.storybook.config.ts
```

This starts Storybook on port 6006, or reuses an existing local Storybook outside CI. Review is the default mode. PNG candidates and failure traces are written under the ignored `test-results/storybook-visual/` directory. Each candidate is attached to its test result and explicitly labelled unapproved.

**A passing capture only means the candidate was created. It is not visual approval and does not pass a visual regression gate.** No baselines have been approved or generated by this change.

## Approve the initial baseline set

1. Select and pin the renderer environment used by CI: OS/image, Playwright and Chromium versions, fonts, and package lock. macOS images must not be promoted for a Linux comparison job.
2. Run candidate capture in that environment from the exact code proposed for acceptance. Review every desktop/mobile and light/dark candidate with Nikhil. Investigate differences or clipping before approval.
3. Only after explicit acceptance, copy each accepted image to `storybook-tests/baselines/<project>/<story-id>.png`. Project names are `desktop-light`, `desktop-dark`, `mobile-light`, and `mobile-dark`. The test filename suffix `.candidate` is removed. Do not copy unreviewed output wholesale.
4. Record the reviewer, review date, renderer environment, and source commit in `visualBaselineApproval` inside `playwright.storybook.config.ts`, then set `approved: true`. Commit the accepted images and completed approval record together.
5. Run comparison in the same pinned environment. No CLI snapshot-update flag is permitted.

The explicit approval manifest currently has `approved: false`. Until acceptance and complete metadata are recorded, comparison fails during configuration; it never silently skips or reports a passing check.

## Compare accepted interfaces

```sh
LANE_VISUAL_MODE=compare pnpm exec playwright test --config playwright.storybook.config.ts
```

Comparison uses `toHaveScreenshot` with snapshot updates disabled and zero differing pixels allowed. A missing baseline fails. A changed baseline fails. The test rejects any CLI override that enables automatic snapshot updates.

For an intentional visual change, return to review mode and obtain acceptance for the changed candidates. Replace only explicitly accepted images, update the approval record to the reviewed source/environment, and rerun comparison. Do not regenerate baselines merely to make a failing job green.

Adding a story to the matrix requires review for every applicable project before that story receives baselines. Missing coverage must remain a failing comparison, not a skip.
